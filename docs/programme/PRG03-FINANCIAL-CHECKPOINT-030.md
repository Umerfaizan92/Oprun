## Restricted credentials and connection validation

For this direct-account integration, the key must be able to retrieve the current account (`GET /v1/account`), account balance and mode (`GET /v1/balance`), tenant payment intent (`GET /v1/payment_intents/:id`), list refunds (`GET /v1/refunds`) and create approved refunds (`POST /v1/refunds`). Give Account, Balance and Payment Intents read access and Refunds read/write access as exposed by Stripe for the selected account/mode. Dashboard grouping can vary. The webhook signing secret is separate and must match the direct-account endpoint and mode.

After saving or rotating the key, the existing payment-settings test checks account identity/mode and Refunds read. A tenant-local sample payment ID verifies PaymentIntent read and mode. The response explicitly marks unsampled PaymentIntent read and Refunds write as unchecked. A read-only probe cannot certify write permission. The owner should inspect the restricted key's grants and obtain separately approved test-mode write evidence before release. An insufficient key gets a generic owner-facing remediation message. Existing claims stay held where identity or evidence is insufficient. Use eligible same-account credentials in the same mode, rerun the read checks, then reconcile outstanding decisions without a new financial operation. Stripe Connect remains unsupported.

## Adjacent handlers and process strategy

Source review found the same missing route-level asynchronous boundary in subscriber PayPal and platform Stripe/Square payment webhooks. PayPal also performs admission, catch cleanup and completion outside its protected block. Resend workspace and platform receipt handlers have asynchronous or storage boundaries with comparable unhandled-rejection exposure. These paths need a separate allocation and fault tests. They were not changed by this Stripe subscriber correction.

Use request boundaries and retryable responses for recoverable operational errors. For unexpected fatal errors, allow Node to exit nonzero and let the service supervisor restart it, with readiness gating, redacted fatal telemetry and restart-loop alerting. An uncaught-exception monitor may observe the fatal error while preserving exit. Do not keep serving from an unknown process state. Redelivery and persistent evidence remain the integrity mechanisms across restart.
