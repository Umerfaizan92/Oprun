- **F1.** A committed claim and original tenant Stripe credential binding precede any financial POST. The owner-only reconcile route reads the original account's paginated refunds. It matches payment intent, tenant and payment evidence, request or provider refund identity, currency and amount. An explicit allowlist of structured Stripe rejections releases a claim. Rate limits, conflicts, unknown 4xx, connection loss and malformed success remain uncertain. An empty read alone never releases a hold. For a new unbound attempt, an active owner may attest a separately verified provider rejection, with an evidence reference, after the in-flight window and a complete read excludes conflicting evidence. A legacy held refund can be linked only when an owner supplies a verified refund ID and evidence reference, provider metadata matches the tenant and payment, and no other local request is a plausible match. Reconciliation and financial POST outcomes are audited. A claimed request is never sent a second time.
- **F2.** Signed standalone Stripe refund events handle pending, requires-action, succeeded, failed and canceled status. The charge aggregate supplies a ledger floor. Where an aggregate overlaps a locally reserved request and embedded receipts are absent or incomplete, the payment remains conservatively held for allocation until a read-only authoritative list can attribute the amounts. Terminal state is retained on delayed pending events. Replay does not debit the same amount twice.
- **F3.** Immediate SQLite transactions protect admission and per-request dispatch. Settlement rereads current payment state and counts completed requests in the same transaction as the payment and work-order updates. Tests used separate OS processes opening independent SQLite connections. A loopback provider barrier observed two distinct financial calls in flight concurrently. Duplicate and over-capacity approvals did not dispatch extra calls.
- **F4.** The receipt is persisted before applying its financial effects. Refund status and both balances commit atomically. A work-order write failure rolled all three back, and the receipt recovered locally with no additional POST. A killed process left a committed claim and no receipt. An exact read-only provider response recovered the operation without another financial call.

Public Stripe contracts reviewed: [Refund object](https://docs.stripe.com/api/refunds/object), [event types](https://docs.stripe.com/api/events/types), [list refunds](https://docs.stripe.com/api/refunds/list), and [error codes](https://docs.stripe.com/error-codes). These describe the standalone refund events, status values, payment-intent filter, pagination and structured error identifiers. No provider account was used.
